**기술 스택**: Vanilla JS, HTML, CSS (의존성 0)
**날짜**: 2026-03-13

## Background

### 채팅 인터페이스의 구조적 한계

AI 코딩 에이전트(Claude Code, Cursor, Cline 등)는 모두 **채팅 또는 CLI 기반 선형 인터페이스**를 쓴다.

이 구조에서는:
- **작업 단계가 뒤섞인다**: 프롬프트 작성, 코드 실행, 결과 리뷰, 의사결정이 하나의 스트림에 섞여서 재사용과 분기가 어렵다
- **데드타임이 집중력을 깬다**: 프롬프트 → 10-30초 대기 → 결과 확인의 반복. 다른 일을 하기엔 짧고, 기다리기엔 긴 시간
- **플랜 검토 지점이 없다**: 에이전트가 계획을 세우고 바로 구현에 들어간다. 사람이 사전에 "이건 하지 마"라고 말할 타이밍이 없다

<!--
AI 코딩 도구를 쓰면서 다들 비슷한 경험을 할 거다. 프롬프트 치고, 10초 정도 기다리고, 결과 보고, 다시 프롬프트 치고. 이 리듬이 꽤 애매하다. 다른 일을 시작하기엔 너무 짧고, 가만히 기다리기엔 좀 길다. 결국 이건 인터페이스 문제다. 채팅이라는 형식이 작업의 각 단계를 분리하지 못하고 하나의 스트림으로 평탄화시키는 거다.
-->

## Solution

### Jupyter에서 영감 받은 셀 기반 AI 코딩 워크스페이스

**한 줄 요약**: 프롬프트 → 플랜 프리뷰(수정/삭제/승인) → 스트리밍 결과 → 셀 재실행

기존 솔루션과 다른 점:

| 기존 도구 | 접근 방식 | 한계 |
|-----------|-----------|------|
| Claude Code, Cursor, Cline | 채팅/CLI 선형 | 단계 분리 불가 |
| Copilot Workspace | 이슈→플랜→코드 파이프라인 | 이슈 기반 선형 워크플로 |
| Plannotator | 플랜 시각 리뷰 | 플랜만 해결, 워크스페이스 아님 |

**우리 접근**: 셀 타입을 분리(Prompt / Plan / Result)하고, 각 셀을 독립 실행 단위로 만든다. 에이전트가 코드를 쓰기 전에 플랜을 먼저 보여주고, 사람이 항목을 수정하거나 빼고 승인한 뒤 실행한다.

<!--
결국 해법은 Jupyter 노트북에서 힌트를 얻었다. 데이터 과학에서 셀 단위로 코드를 나눠서 실행하는 게 당연한 것처럼, AI 코딩 작업도 프롬프트, 플랜, 결과를 별도 셀로 나누면 된다. 핵심은 에이전트가 바로 코드를 쓰는 게 아니라, 플랜을 먼저 체크리스트로 보여주고, 사람이 그걸 수정하거나 빼고 승인하면 그때 실행하는 거다. 사람으로 치면, 의사가 수술 전에 수술 계획서를 환자에게 보여주는 것과 마찬가지다.

│  └─────┬─────┘    └────────────┘    └────────┬──────────┘   │
│        │                                     │              │
│        ▼                                     ▼              │
│  ┌──────────────────────────────────────────────────────┐   │
│  │                    app.js (핵심 로직)                 │   │
│  │  cells[] ─── 상태 관리 ─── cellIdCounter             │   │
│  │     │                                                │   │
│  │  ┌─────────┐  ┌─────────┐  ┌──────────┐             │   │
│  │  │ Prompt  │─▶│  Plan   │─▶│  Result  │             │   │
│  │  │  Cell   │  │  Cell   │  │  Cell    │             │   │
│  │  │ (idle)  │  │(preview)│  │(stream→  │             │   │
│  │  │         │  │         │  │  done)   │             │   │
│  │  └─────────┘  └─────────┘  └──────────┘             │   │
│  └──────────────────┬──────────────────────────────────┘   │
│                     ▼                                       │
│  ┌────────────────────────┐   ┌───────────────────┐        │
│  │      render.js         │   │   LocalStorage     │        │
│  │ (셀 DOM 생성·이벤트)   │   │  (상태 영속화)     │        │

└─────────────────────────────────────────────────────────────┘

- **app.js**: 셀 생성/삭제, 실행 흐름, 플랜 승인, 상태 저장 (216줄)
- **render.js**: DOM 생성과 이벤트 바인딩, XSS 방지를 위해 innerHTML 미사용 (156줄)
- **mock-data.js**: 사전 정의된 AI 응답 시나리오 (47줄)

<!--

### Prompt → Plan Preview → Approve → Streaming Result

```
[Prompt Cell]  "React Todo 앱에 필터 기능을 추가해줘..."
      │
      ▼  Run 클릭 (또는 Ctrl+Enter)
[Plan Cell]   ✅ TodoList 컴포넌트에서 필터 상태를 관리할 state 추가
              ✅ FilterBar 컴포넌트 생성
              ✅ 필터 조건에 따라 todo 목록 필터링
              ✅ FilterBar에 활성 필터 하이라이트 스타일 적용
              ✅ URL 해시 업데이트
      │
      ▼  항목 수정/삭제 후 "Approve & Execute"

               └──────────────────────────────┘
```

<!--

## Key Decisions & Lessons

### 기술 판단

| 판단 | 선택 | 이유 |
|------|------|------|
| 스택 | Vanilla JS, 의존성 0 | 프론트엔드 전용 프로토타입. 즉시 실행 가능, 빌드 불필요 |
| AI 응답 | Mock 기반 | 실제 API 없이 워크플로 자체를 검증하는 게 목적 |
| 테스트 | jsdom (Playwright/Puppeteer 실패) | 시스템 라이브러리 부재로 브라우저 테스트 불가 → jsdom 전환 |
| 파일 구조 | 단일 파일 → 4파일 분리 | 셀프 크리틱에서 745줄 단일 파일 문제 지적 → 분리 |

### 심의 점수

| 항목 | 점수 |
|------|------|
| 문제 진정성 | 4.0 / 5 |
| 프로토타입 적합성 | 2.7 / 5 |
| 신선도 | 3.3 / 5 |
| 학습 가치 | 3.7 / 5 |

**반대 의견**: "mock API 기반 데모로는 셀 기반이 더 낫다는 핵심 가설을 실질적으로 검증하기 어렵다" (준혁)

<!--
스택 선택은 꽤 명확했다. 검증하려는 건 셀 기반 워크플로 자체이지, 특정 프레임워크가 아니다. 그래서 React도 안 쓰고 vanilla JS로 갔다. 의존성 0이니까 index.html 열면 바로 된다. 시행착오가 하나 있었는데, 테스트를 Playwright로 하려다 시스템 라이브러리가 없어서 실패했다. jsdom으로 전환해서 30개 테스트 전부 통과시켰다. 심의에서 프로토타입 적합성이 2.7로 낮은 편인데, 준혁이 지적한 대로 mock 기반으로는 정량적 비교가 어렵다는 한계가 있다. 솔직히 이건 맞는 말이다.
-->

## Results & Future

### 완료 기준 결과: 5/5 통과

- [x] 프롬프트 셀 실행 → mock 응답 스트리밍 표시
- [x] 플랜 프리뷰: 체크리스트 + 삭제/수정/승인
- [x] 셀 단위 독립 재실행
- [x] 코딩 시나리오 데모 (React Todo 필터 기능)
- [x] LocalStorage 상태 저장/복원

### 한계점
- Mock 기반이라 실제 AI 응답 품질과의 연동은 미검증
- 셀 간 의존성 그래프(DAG) 미구현
- 드래그앤드롭 셀 재배치 미구현

### 프로덕트가 되려면
- **실제 LLM 연동**: Claude API / OpenAI API와 붙여서 실제 코드 생성 품질 검증
- **셀 간 의존성**: 한 셀의 결과가 다른 셀의 입력이 되는 DAG 구조
- **파일 시스템 통합**: 실제 프로젝트 디렉토리의 코드를 읽고 쓰는 기능
- **정량적 비교**: 채팅 대비 작업 완료 시간, 재작업 횟수 등 측정
