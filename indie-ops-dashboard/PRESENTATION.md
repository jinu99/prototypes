## Background

솔로 개발자가 늘고 있다. 사이드 프로젝트든 인디해커든, 혼자서 프로덕션 인프라를 운영하는 사람이 많아졌다.

문제는 이 사람들이 **엔터프라이즈급 인프라 도구**와 **아무 도구도 안 쓰는 것** 사이에 끼어 있다는 거다.

- Datadog, New Relic → 솔로 개발자에겐 과하고 비싸다
- Uptime Kuma, Healthchecks.io → 각각 하나만 해결한다
- 결국 3-4개 도구를 조합하거나, 아예 모니터링 없이 운영한다

**"소규모 팀에 맞는 인프라 가시성"**이 구조적으로 부재한 상황이다.

<!--
개발자 생태계에서 솔로 개발자가 점점 늘고 있다. 근데 이 사람들이 겪는 공통적인 문제가 있다. 인프라 모니터링 도구가 너무 크거나, 너무 작거나, 둘 중 하나라는 거다. Datadog 같은 건 솔로한테 과하고, Uptime Kuma 같은 건 업타임만 본다. 결국 여러 도구를 조합해야 하는데, 솔로 개발자한테 그건 또 다른 운영 부담이다.
-->

## Solution

**한 줄 요약**: 서버 리소스 패턴을 자동 분석해서 "하루 N시간만 활성 → 서버리스 전환 시 월 $X 절감" 인사이트를 제공하는 셀프호스팅 대시보드

### 기존 도구와 다른 점

| 기존 도구 | 하는 일 | 안 하는 일 |
|-----------|---------|-----------|
| Uptime Kuma | 업타임 모니터링 | 비용 분석, 크론 감시 |
| Healthchecks.io | 크론 누락 감지 | 중복 실행 감지, 비용 분석 |
| Cronboard | 크론 충돌 감지 (베타) | 업타임, 비용 분석 |

→ **이 대시보드**: 메트릭 수집 + 패턴 분석 + 비용 비교 + 업타임 + 크론을 **하나의 경량 도구**로 통합

<!--
접근법은 이렇다. 서버의 CPU, 메모리를 30초마다 수집해서 활성 구간과 유휴 구간을 자동으로 분류한다. 그 패턴을 기반으로 EC2 24시간 비용과 Lambda로 전환했을 때 비용을 비교해준다. 기존 도구들은 업타임, 크론, 비용을 각각 따로 봐야 한다. 이걸 하나의 가벼운 대시보드에 넣은 게 차별점이다.
-->

## Architecture

```
┌─────────────────────────────────────────────────────────────┐
│  Collection Layer                                           │
│  collector.py (30초 주기)       uptime.py (HTTP retry 2회) │
│   psutil: CPU/Mem/Net            httpbin.org, example.com   │
└──────────────┬─────────────────────────┬────────────────────┘
               ▼                         ▼
┌─────────────────────────────────────────────────────────────┐
│  database.py — SQLite (metrics.db)                          │
│  metrics │ uptime_checks │ cron_heartbeats                  │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────┐
│  analyzer.py                                                │
│  CPU ≥ 10% → active / < 10% → idle                         │
│  시간대별 세그먼트 → EC2 vs Lambda 비용 비교 산출           │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────┐
│  server.py — FastAPI :8099                                  │
│  REST API (7 endpoints) + static/index.html (Chart.js)      │
│  시계열 차트 │ 세그먼트바 │ 비용비교 │ 업타임 │ 크론       │
└─────────────────────────────────────────────────────────────┘
```

- **수집**: psutil로 30초마다 CPU/메모리/네트워크 → SQLite 적재
- **분석**: CPU 10% 임계치로 활성/유휴 분류 → 일별 활성 시간 산출 → Lambda 비용 추정
- **표현**: FastAPI + Chart.js 단일 페이지 대시보드

<!--
구조는 세 겹이다. 수집 레이어에서 psutil로 30초마다 시스템 메트릭을 긁어서 SQLite에 넣는다. 분석 레이어에서 CPU 사용률 10% 기준으로 활성과 유휴를 나누고, 그 비율로 Lambda 전환 비용을 계산한다. 표현 레이어는 FastAPI에 Chart.js 단일 HTML이다. 전체가 Python 파일 7개, 외부 의존성은 psutil과 aiosqlite 정도다. 꽤 가볍다.

```json

    "monthly": 5.26,
```

### 대시보드 구성

다크 테마 2-컬럼 레이아웃:
- **메인**: CPU/Memory 시계열 → Active/Idle 세그먼트바 → 일별 활성 시간 → EC2 vs Lambda 비용 그리드
- **사이드바**: Uptime 상태 (●/● + 응답시간) · Cron Heartbeat 요약 (마지막 수신 + 횟수)

## Key Decisions & Lessons

### 1. FastAPI lifespan으로 별도 프로세스 없이 수집
- `asynccontextmanager`로 서버 시작 시 메트릭 수집 태스크를 백그라운드로 실행
- 별도 데몬이나 crontab 설정 없이 `uvicorn server:app` 하나로 전부 동작
- 솔로 개발자에게 "실행 명령어 하나"는 채택 장벽을 크게 낮춤

### 2. Lambda 비용 모델 조정 — 셀프 크리틱에서 발견
- 처음엔 100 req/hr + 128MB → Free Tier에 흡수돼서 Lambda 비용이 **$0**으로 나옴
- 비현실적이라 5,000 req/hr + 256MB/500ms + Free Tier 제외로 상향
- EC2 $7.59 → Lambda $2.33, 69.3% 절감 — 의미 있는 비교가 됨

### 3. 심의 점수와 범위 타협
- 문제 진정성 3.7 / 프로토타입 적합성 2.7 / 신선도 2.7 / 학습 가치 3.7
- 반대 의견: "업타임은 Uptime Kuma retry, 크론은 flock으로 이미 해결됨"
- → 범위를 **비용 분석에 집중**, 업타임·크론은 통합 뷰 컨셉 시연 수준으로 축소

<!--
기술적으로 몇 가지 판단이 있었다. 첫째, FastAPI의 lifespan을 써서 서버 하나 띄우면 메트릭 수집도 같이 돌아가게 했다. 솔로 개발자한테 실행 명령어가 하나라는 건 꽤 중요하다. 둘째, Lambda 비용 모델이 처음에 너무 보수적이어서 0달러가 나왔다. 셀프 크리틱 단계에서 이걸 발견하고 현실적인 파라미터로 조정했다. 셋째, 심의에서 업타임이랑 크론은 기존 도구로 충분하다는 반대 의견이 있었다. 맞는 지적이라 비용 분석에 포커스를 맞추고 나머지는 통합 뷰 컨셉 정도로 줄였다.
-->

## Results & Future

### 성과 (5/5 통과)
- ✓ 시스템 메트릭 30초 간격 수집 → SQLite (4,300+ rows)
- ✓ 활성/유휴 자동 분류 + "하루 N시간 활성" 산출
- ✓ EC2 vs Lambda 비용 비교 + 자동 추천 메시지
- ✓ 시계열 + 세그먼트 + 비용비교 통합 대시보드
- ✓ 업타임 + 크론 하트비트 사이드 패널

### 한계
- 비용 모델이 하드코딩 가격표 기반 — 실제 AWS API 연동은 미포함
- 단일 서버 메트릭만 수집 — 다중 서버 지원 없음
- 알림/노티피케이션 시스템 없음

### 프로덕트가 되려면
- 실제 클라우드 API 연동 (AWS Cost Explorer, GCP Billing)
- 멀티 서버 에이전트 + 중앙 집계
- Slack/Discord 알림 통합
- "서버리스 전환하면 이렇게 바꿔라"는 구체적 마이그레이션 가이드 생성
