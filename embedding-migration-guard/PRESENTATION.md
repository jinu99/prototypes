# Embedding Migration Guard

**임베딩 모델 교체 전, CLI 한 줄로 recall@k 드롭을 예측한다**

- 카테고리: RAG / Vector Search 인프라
- 스택: Python, sentence-transformers, NumPy, Click, uv
- 날짜: 2026-03-12

# Background

## 임베딩 모델 교체는 RAG의 가장 비싼 작업이다

- RAG 파이프라인의 핵심은 임베딩 모델. 더 좋은 모델이 나오면 바꾸고 싶다
- 문제는 모델을 바꾸면 **기존 벡터 인덱스 전체를 재구축**해야 한다는 것
- 수백만 문서 코퍼스에서 재인덱싱은 수 시간~수일, 비용은 수백 달러 이상
- 그래서 대부분의 팀은 **모델 업그레이드를 미룬다**

## 2026년 현재, 마이그레이션 전용 도구는 없다

- LlamaIndex, LangChain 모두 "모델 바꾸면 전체 재인덱싱" 전제
- 벡터 DB(Qdrant, Pinecone)도 모델 전환 워크플로 미제공
- "바꿔도 되는지" 미리 검증하는 도구 자체가 부재

<!--
RAG 시스템을 운영하다 보면, 더 좋은 임베딩 모델이 계속 나온다. 그런데 모델을 바꾸면 기존에 만들어둔 벡터 인덱스가 전부 쓸모없어진다. 전체 재인덱싱을 해야 하는데, 대규모 코퍼스에서는 비용도 시간도 만만치 않다. 결국 대부분의 팀이 모델 업그레이드를 미루게 된다. 그리고 현재 시점에서 "바꿔도 괜찮은지"를 미리 확인해주는 도구는 없다. LlamaIndex든 LangChain이든 전부 전체 재인덱싱을 당연시한다.
-->

# Solution

## 교체 전에 예측한다, 교체 후에 후회하지 않게

**한 줄 요약**: `emg check` 한 번이면 두 모델 간 recall@k 드롭을 미리 알 수 있다

### 기존 방식과의 차이

| | 기존 방식 | EMG |
|---|---|---|
| 검증 시점 | 교체 후 (사후 확인) | 교체 전 (사전 예측) |
| 비용 | 전체 재인덱싱 필요 | 샘플 코퍼스로 수 초 |
| 판단 기준 | 감, 경험 | recall@k, NN overlap, cosine 분포 |
| 결과물 | 없음 | JSON 리포트 (CI 연동 가능) |

<!--
기존에는 모델을 바꾸고 나서야 문제를 발견했다. 전체 재인덱싱을 하고 나서 recall이 떨어지면 롤백하는 식이었다. EMG는 순서를 뒤집는다. 바꾸기 전에 샘플 코퍼스로 recall@k 드롭을 예측한다. 수 초면 끝나고, 리스크 등급까지 자동으로 나온다. 결국 이건 의사결정 도구다. 바꿔도 되는지 안 되는지를 데이터로 판단하게 해준다.
-->

# Architecture

```
┌─────────────────────────────────────────────────────────────┐
│                       CLI (cli.py)                          │
│            check / demo 서브커맨드 (Click)                    │
└──────────┬──────────────────────────────────┬───────────────┘
           │                                  │
           ▼                                  ▼
┌─────────────────────┐            ┌─────────────────────────┐
│   Corpus Loader     │            │   Model Loader          │
│   (embedder.py)     │            │   (embedder.py)         │
│ • 텍스트 파일 로드    │            │ • SentenceTransformer   │
│ • 디렉토리 스캔      │            │   모델 2개 로드 (old/new)│
└────────┬────────────┘            └────────┬────────────────┘
         │                                  │
         ▼                                  ▼
┌─────────────────────────────────────────────────────────────┐
│              Comparator (comparator.py)                      │
│  Pairwise Cosine │ NN Overlap (Jaccard) │ Recall@K          │
└──────────────────┼──────────────────────┼───────────────────┘
                   ▼                      ▼
┌─────────────────────────────────────────────────────────────┐
│  Report (report.py) — Risk 판정 + 콘솔 출력 + JSON export   │
└─────────────────────────────────────────────────────────────┘
```

- **4개 모듈**, 각각 단일 책임. 전체 코드 약 300줄
- ChromaDB 의존성은 포함했지만, 110문서 규모에서는 NumPy in-memory가 더 빠르고 단순

<!--
구조는 단순하다. 4개 모듈이 각각 하나의 역할만 한다. embedder가 코퍼스와 모델을 로드하고, comparator가 세 가지 메트릭을 계산하고, report가 결과를 보여준다. CLI가 이걸 엮어주는 역할. 처음에는 ChromaDB를 벡터 DB로 쓰려고 했는데, 110개 문서에서는 NumPy 직접 연산이 훨씬 빠르고 간단해서 그쪽으로 갔다. 대규모로 확장할 때 ChromaDB를 붙이면 된다.
-->

# Key Decisions & Lessons

## 기술 판단

| 판단 | 선택 | 이유 |
|------|------|------|
| 벡터 DB | NumPy in-memory | 110문서에서 ChromaDB보다 빠르고 단순. 확장 시 교체 가능 |
| CLI 프레임워크 | Click | 서브커맨드 구성이 깔끔. argparse보다 선언적 |
| 리스크 판정 | recall@10 + NN overlap 조합 | 단일 메트릭보다 robust. recall만으로는 false positive 많음 |

## 심의 피드백

- **문제 진정성**: 4.0/5 — 실제로 커뮤니티에서 반복 제기되는 문제
- **프로토타입 적합성**: 3.3/5 — 검증 목표가 명확하고 범위가 적절
- **반대 의견**: "cosine 분포 비교 + recall 측정은 notebook 수준, Drift-Adapter 같은 비자명한 접근이 빠져 있다"
- 솔직히 기술적 깊이는 얕은 편. 하지만 **문제 정의와 UX에 집중**한 프로토타입

<!--
기술 판단 몇 가지를 공유하면. ChromaDB를 의존성에 넣어놓고 결국 안 썼다. 110문서에서는 NumPy가 더 낫다. 이건 프로토타입이니까 적절한 판단이었다고 본다. 리스크 판정은 recall@10 하나만 보는 것보다 NN overlap을 같이 보는 게 더 안정적이었다. 심의에서 준혁이 "이건 notebook 수준 아니냐"라는 지적을 했는데, 맞는 말이다. 기술적 도전이 깊진 않다. 다만 이 프로토타입의 가치는 기술적 깊이보다 "이 문제를 CLI 한 줄로 풀 수 있다"는 UX에 있다고 본다.

# Results & Future

## 성과 (5/5 통과)

- ✅ `emg check`으로 벡터 공간 차이 리포트 출력
- ✅ recall@k 비교 결과 출력 (recall@1, @5, @10)
- ✅ 100+ 문서에서 30초 이내 완료 (110문서, 7.7초)
- ✅ JSON export (CI 파이프라인 연동용)
- ✅ `emg demo`로 전체 워크플로 시연

## 한계

- sentence-transformers 모델만 지원 (OpenAI, Cohere 등 API 모델 미지원)
- 차원이 다른 모델 간 비교 불가 (projection 미구현)
- Drift-Adapter 같은 linear adapter 학습은 범위 밖

## 프로덕트가 되려면

- API 기반 임베딩 모델 지원 (OpenAI, Cohere, Voyage)
- 프로덕션 벡터 DB에서 직접 샘플링 (Pinecone, Weaviate 연동)
- Drift-Adapter: 두 벡터 공간 사이의 linear mapping 학습으로 재인덱싱 없이 마이그레이션
- GitHub Action / CI 플러그인으로 모델 업그레이드 PR에 자동 리포트 첨부
