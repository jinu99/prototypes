## Background

### 소규모 매장의 대기열 관리는 아직 아날로그다

- 카페, 레스토랑, 미용실 — 여전히 **종이 명단**이나 **수동 메시지**로 대기열을 관리
- 기존 SaaS 솔루션(ScanQueue, Carbonara)은 **월 구독료**가 부담이거나 기능이 과도함
- 셀프호스팅 가능한 현대적 대안이 사실상 없음
  - GitHub의 레거시 프로젝트들은 PhoneGap 기반, 실사용 불가

> 비개발자 매장 운영자가 **5분 내 설치해서 바로 쓸 수 있는** 대기열 도구가 없다

<!--

## Solution

### 접근법: QR 하나로 끝나는 대기열

**검증 목표**: 비개발자 매장 운영자가 QR 코드 하나로 고객 대기열을 디지털 관리하고, 실시간 대기 순서 표시로 고객 이탈을 줄일 수 있는가?

**기존 솔루션과의 차이점:**

| 기존 | Small Biz Queue Ops |
|------|---------------------|
| SaaS 구독 모델 | 셀프호스팅, 무료 |
| 복잡한 설정, 회원가입 | `npm start` 한 줄 실행 |
| 기업용 기능 과다 | QR 등록 + 상태 관리 + KDS, 딱 필요한 것만 |
| 외부 의존성 (SMS, 클라우드) | SQLite + SSE, 외부 의존 없음 |

<!--
우리 접근은 단순하다. QR 코드 하나를 매장에 붙이면, 고객이 스캔해서 대기열에 등록하고, 매장에서는 실시간으로 관리한다. 기존 솔루션과 다른 건 세 가지다. 구독료 없이 셀프호스팅이 가능하고, npm start 한 줄이면 끝나고, 딱 필요한 기능만 있다. 사람으로 치면, 종이 명단을 디지털로 옮긴 거지 ERP를 매장에 들여온 게 아니다. 적정 기술이 핵심이다.
-->

## Architecture

```
┌──────────────────────────────────────────────────────────────────┐
│                        클라이언트 (Browser)                       │
│  ┌────────────┐  ┌────────────┐  ┌────────────┐  ┌────────────┐ │
│  │ index.html │  │ join.html  │  │ admin.html │  │  kds.html  │ │
│  │  홈 / QR   │  │ 대기 등록  │  │ 매장 관리  │  │  KDS 뷰   │ │
│  └─────┬──────┘  └─────┬──────┘  └─────┬──────┘  └─────┬──────┘ │
│        └───────────┬────┴───────────────┴───────┬───────┘        │
│              REST API (fetch)            SSE (EventSource)       │
└──────────────────┬───────────────────────────┬───────────────────┘
                   ▼                           ▼
┌─────────────────────────────────────────────────────────────────┐
│  server.js → routes.js (CRUD) ──broadcast──▶ sse.js (실시간)    │
│                  │                                               │
│                  ▼                                               │
│             db.js (SQLite)                                       │
└─────────────────────────────────────────────────────────────────┘
```

- **routes.js**: 대기열 CRUD + QR 생성 — 상태 변경 시 자동 broadcast
- **sse.js**: SSE 클라이언트 관리 — 20줄로 실시간 푸시 구현
- **db.js**: SQLite 초기화 — 상태 전이 타임스탬프 자동 기록

<!--
아키텍처는 의도적으로 단순하게 잡았다. Node.js 내장 http 모듈 위에 routes, sse, db 세 개 모듈만 올린다. 프론트엔드는 4개의 HTML 파일이 REST API로 데이터를 주고받고, SSE로 실시간 업데이트를 받는다. SSE 모듈은 20줄짜리인데, 이게 전체 실시간 기능을 담당한다. Express도 안 쓰고, WebSocket도 안 쓴다. 매장 대기열 관리에 복잡한 양방향 통신이 필요하지 않으니까. SSE가 이 문제에 맞는 적정 기술이다.
-->

## Demo

### 핵심 Flow: 등록 → 관리 → 실시간 갱신

**1. 대기 등록 (고객)**
```bash
POST /api/queue  {"name": "홍길동", "party_size": 4}
→ {"id":1, "position":1, "estimated_wait":0, "status":"waiting"}
```

**2. 상태 변경 (매장)**
```bash
PATCH /api/queue/1/status  {"status": "called"}
→ {"id":1, "status":"called", "called_at":"2026-03-16 14:30:00"}
```

**3. 실시간 갱신 (SSE)**
```
event: queue-update
data: [{"id":1,"status":"called","position":null}, ...]
```

> 상태 전이: `waiting → called → seated → completed`
> 각 단계마다 타임스탬프 자동 기록, 전체 클라이언트에 즉시 broadcast

<!--
실제 동작을 보면, 고객이 QR을 스캔하고 이름과 인원수를 넣으면 대기열에 등록된다. 대기 순서와 예상 시간이 바로 나온다. 매장 관리자가 상태를 바꾸면, 그 순간 모든 클라이언트에 SSE로 업데이트가 간다. waiting에서 called, seated, completed까지 4단계 전이가 있고, 각 단계에서 타임스탬프가 자동으로 찍힌다. 고객 입장에서는 내 차례가 언제인지 실시간으로 보이니까, 종이 명단에서 느끼는 불확실성이 없어진다.
-->

## Key Decisions & Lessons

### 기술 판단

| 판단 | 선택 | 이유 |
|------|------|------|
| 프레임워크 | Node.js 내장 `http` | Express 불필요 — API 6개에 프레임워크는 과하다 |
| 실시간 통신 | SSE (Server-Sent Events) | 대기열은 서버→클라이언트 단방향 — WebSocket 불필요 |
| DB | better-sqlite3 | 동기 API로 코드가 단순, 단일 서버에 적합 |
| 프론트엔드 | Vanilla JS + 4 HTML | React/Vue는 이 규모에서 오버헤드만 추가 |

### 심의 점수

| 항목 | 점수 | 비고 |
|------|------|------|
| 문제 진정성 | 3.7/5 | 실제 pain point가 명확 |
| 프로토타입 적합성 | 4.3/5 | 하루 만에 검증 가능한 범위 |
| 신선도 | 2.7/5 | CRUD+SSE 패턴의 반복이라는 반대 의견 |
| 학습 가치 | 2.7/5 | 기술적으로 비자명한 도전은 적음 |

<!--
기술 선택에서 일관된 원칙이 하나 있다. 필요한 것만 쓴다. API가 6개인데 Express를 쓸 이유가 없고, 서버에서 클라이언트로 단방향 푸시만 하면 되는데 WebSocket을 쓸 이유가 없다. 심의에서 준혁이 기술적으로 비자명한 도전이 없다고 했는데, 솔직히 맞는 말이다. CRUD에 SSE를 붙인 거니까. 다만 이 프로토타입의 가치는 기술 난이도가 아니라, 적정 기술로 실제 문제를 풀 수 있는지 검증하는 데 있다. 꼭 어려운 기술을 써야 의미 있는 건 아니다.
-->

## Results & Future

### 성과: 5/5 완료 기준 전부 통과 ✅

- [x] QR 코드 스캔 → 이름/인원수 입력 → 대기열 등록 flow 동작
- [x] 실시간 대기 순서 + 예상 시간 자동 갱신 (SSE)
- [x] 매장 관리 화면: 대기자 목록, 상태 변경 (대기→호출→착석→완료)
- [x] KDS 뷰 (카드 형태 대기 상태 디스플레이)
- [x] `npm start` 한 줄 실행

### 한계점
- 인증 없음 — 관리자 페이지에 아무나 접근 가능
- SMS/푸시 알림 없음 — 고객이 브라우저를 닫으면 호출을 못 받음
- Playwright 테스트 불가 — curl 기반 검증으로 대체

### 프로덕트가 되려면
- 기본적인 인증 (매장별 관리자 PIN 정도)
- 고객 알림 채널 (SMS, 카카오톡, 웹 푸시)
- Docker 패키징 + 원클릭 배포
- 매장별 커스터마이징 (로고, 대기 시간 알고리즘)
