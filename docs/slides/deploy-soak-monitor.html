Deploy Soak Monitor

배포 후 자동 soak 윈도우 모니터링 — pod 상태/로그 실시간 감시로 이상 징후를 잡아내는 CLI 도구

  • 카테고리: DevOps / Kubernetes Observability
  • 스택: Python 3.12, asyncio, 외부 의존성 0개
  • 날짜: 2026-03-14

Background

배포 후 15분, 개발자는 뭘 하고 있나

  • 프로덕션 배포 직후 10~15분간 개발자가 수동으로 감시하는 "soak 구간"이 존재
  • Grafana 대시보드, 에러 로그, 알림 채널을 번갈아가며 모니터링
  • 야간 배포, 하루 여러 번 배포하는 팀일수록 부담이 기하급수적으로 증가
  • Kubernetes 환경에서는 kubectl, k9s, Lens, 브라우저를 전전하며 도구 전환

배포는 자동화됐는데, 배포 직후 감시는 여전히 수동이다.

Pain Point

커뮤니티에서 반복적으로 나오는 고통

#출처SignalPain Point
1HN★★★배포 직후 10~15분간 수동 모니터링 구간이 반복된다

5HN★★★K8s 관리가 kubectl, k9s, Lens, 브라우저에 분산
6Reddit★★★20개 사이트 관리 중 일요일 아침 긴급 연락 수신

Solution

모든 배포에 자동으로 붙는 가벼운 soak monitor

핵심 아이디어: 서비스 메시 없이, "배포 후 N분간 자동 감시 → 이상 시 알림"

기존 솔루션한계이 도구의 접근
K8sGPTon-demand 진단 (사후)배포 이벤트 자동 감지 후 실시간 감시
Argo Rollouts / Flagger서비스 메시 필요, setup 부담의존성 0개, CLI 하나로 즉시 사용
Botkube프리미엄, Slack 의존터미널 기반, 롤백 명령까지 제안

검증 목표: 배포 후 MTTD(평균 감지 시간)를 5분 이내로 줄일 수 있는가?

Architecture

┌─────────────────────────────────────────────────────────────────┐
│                          CLI (cli.py)                           │
│                   argparse: watch / scenarios                   │
└──────────────────────────┬──────────────────────────────────────┘
                           │ Command parsing
                           ▼
┌──────────────────────────────────────────────────────────────────┐
│                    Demo Runner (demo.py)                         │
│        Scenario select: healthy │ oom │ crashloop │ error_logs     │
└──────────────┬──────────────────────────────────┬────────────────┘
               │ create_deployment()              │ rolling_update()
               ▼                                  ▼
┌──────────────────────────────────────────────────────────────────┐
│                 Simulated Cluster (cluster.py)                   │
│   Deployment/Pod create → Fault inject (OOM/CrashLoop/Log) → Emit event │
└──────────────────────────────────────────┬───────────────────────┘
                                           │ watcher callback
                                           ▼
┌──────────────────────────────────────────────────────────────────┐
│                   Soak Monitor (monitor.py)                      │
│   Event receive → Pod status check → Log analysis (PatternMatcher, 9 regex) │
└──────────────────────────────────────────┬───────────────────────┘
                                           │ anomaly / pattern_alert
                                           ▼
┌──────────────────────────────────────────────────────────────────┐
│                     Reporter (reporter.py)                       │
│   ✓ Pod started │ ↻ Rolling Update │ ✖ Issue detected │ ⚠ Anomaly  │
│   Progress Bar [████░░░░] 40%  │  ALL CLEAR / SOAK FAILED       │
└──────────────────────────────────────────────────────────────────┘

Key Decisions & Lessons

기술 판단

판단이유
Go 대신 Python 선택Go/kubectl/kind 모두 미설치 환경. Python 3.12 + uv로 즉시 시작
K8s 시뮬레이터 방식실제 클러스터 없이 전체 흐름 검증. 인터페이스 분리로 추후 교체 용이
외부 의존성 0개표준 라이브러리(asyncio, re, argparse)만으로 전체 구현

시행착오

  • error_logs 시나리오에서 connection_refused + error_generic 중복 매칭 발생
  • → 가장 높은 severity 패턴만 보고하도록 수정 (priority map 기반 필터링)

Results & Future

성과

  • soak watch <namespace> — Deployment 변경 자동 감지
  • 새 pod 로그 스트리밍 + 에러 패턴 매칭 (9개 정규식)
  • soak 윈도우 + --duration 플래그 지원
  • 이상 감지 시 경고 + kubectl rollout undo 제안
  • 4개 장애 시나리오 데모 동작 (healthy, oom, crashloop, error_logs)
  • 심의 패널: 만장일치 승인 · 완료 기준 전항 통과

한계

  • 실제 K8s 클러스터 연동 미구현 (시뮬레이터만)
  • Slack/webhook 알림 미연동 (터미널 출력만)
  • 환경 간 설정 드리프트 탐지 미포함 (scope 축소)
  • 자동 롤백은 명령 제안만 (실행은 사람이)

프로덕트가 되려면

  1. cluster.py → 실제 kubernetes client 교체 (인터페이스 동일)
  2. Slack/PagerDuty webhook 알림 연동
  3. Prometheus 메트릭 기반 이상 탐지 추가
  4. CI/CD 파이프라인 연동 (배포 이벤트 자동 트리거)
