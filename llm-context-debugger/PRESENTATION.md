# LLM Context Debugger

**OpenAI API 프록시로 컨텍스트 윈도우의 토큰 구성을 실시간 분석·시각화**

- 카테고리: LLM DevTool / Observability
- 스택: Python, FastAPI, tiktoken, vanilla JS
- 날짜: 2026-03-08

## Background

- LLM 에이전트 시대: 시스템 프롬프트 + 대화 히스토리 + 도구 정의 + 도구 결과가 하나의 컨텍스트 윈도우에 합쳐진다
- 컨텍스트는 **유한한 자원**인데, 이 자원이 어떻게 쓰이는지 볼 수 있는 방법이 없다
- Langfuse, Braintrust 같은 관측 도구는 "호출 단위" 분석 — 컨텍스트 **내부 구성**은 블랙박스
- CLAUDE.md가 비대해지고, 도구 카탈로그가 수천 개로 늘어나면 문제는 더 심각해진다

<!--
LLM 에이전트 개발할 때 가장 기본적인 질문이 있다. 지금 이 에이전트한테 보내는 컨텍스트 안에 뭐가 들어가 있는가. 시스템 프롬프트가 얼마나 큰지, 도구 정의가 토큰을 얼마나 먹는지, 히스토리가 누적되면서 뭐가 밀려나는지. 기존 관측 도구들은 API 호출 로그를 보여주긴 하는데, 컨텍스트 윈도우 안쪽까지 들여다보진 않는다. 결국 이건 관측 레이어가 하나 빠져있는 거다.
-->

## Solution

**한 줄 요약**: API base URL만 바꾸면 컨텍스트 구성이 보인다

핵심 아이디어:
- 기존 도구: 호출 **로그**를 추적 → "무슨 API를 불렀는가"
- 우리 도구: 호출 **내부**를 분해 → "컨텍스트가 어떻게 구성되었는가"

차별점:
1. **코드 수정 제로** — `base_url`만 프록시로 변경
2. **토큰 수준 분해** — tiktoken으로 컴포넌트별 정확한 토큰 카운팅
3. **연속 호출 diff** — 대화가 진행되면서 컨텍스트가 어떻게 변하는지 추적
4. **로컬 실행** — 데이터가 외부로 나가지 않음

<!--
접근법은 꽤 단순하다. LLM API 호출을 로컬 프록시로 중간에 가로채서, 컨텍스트 윈도우를 토큰 단위로 분해하는 거다. 기존 Langfuse나 LiteLLM은 호출 로그를 추적하는데, 우리는 호출 내부를 들여다본다. 레이어가 다르다. 그리고 에이전트 코드를 건드릴 필요가 없다. base_url 하나만 바꾸면 된다.
-->

## Architecture

```
┌─────────────────┐       ┌──────────────────────────────────────────────┐
│  OpenAI Client  │       │        FastAPI Proxy (proxy.py:8088)        │
│                 │  POST │                                              │
│  base_url =     ├──────▶│  ┌──────────────────┐  ┌─────────────────┐  │
│  localhost:8088 │       │  │ Token Analyzer   │  │ In-Memory Store │  │
└─────────────────┘       │  │ (token_counter)  │─▶│ (store.py)      │  │
                          │  │ tiktoken-based    │  │ CallRecord+diff │  │
                          │  └──────────────────┘  └────────┬────────┘  │
                          └──────────────┬──────────────────┼───────────┘
                            Forward ─────┘                  │
                            (real mode)                     ▼
                          ┌──────────────┐       ┌──────────────────────┐
                          │ OpenAI API   │       │ Dashboard (HTML)     │
                          │ (upstream)   │       │ bar chart·treemap·diff│
                          └──────────────┘       └──────────────────────┘
```

- **proxy.py**: Request intercept + mock/real mode switching
- **token_counter.py**: Per-message token breakdown, 5-component classification
- **store.py**: Call record storage + inter-call diff computation
- **dashboard.html**: Real-time visualization with 2s polling

<!--
구조는 3개 파일이 핵심이다. proxy.py가 FastAPI로 요청을 받아서, token_counter.py가 tiktoken으로 메시지를 분해하고, store.py가 기록을 쌓으면서 호출 간 diff를 계산한다. 대시보드는 단일 HTML 파일이고 2초 간격으로 폴링한다. mock 모드가 있어서 API 키 없이도 테스트할 수 있고, real 모드면 원래 OpenAI API로 그대로 전달한다.

## Demo

### 프록시 콘솔 출력
```
============================================================
[Call #1] model=gpt-4 total=24 tokens
  system: 13 (54.2%)
  user: 8 (33.3%)
  ⚠ WARNING: system uses 54.2% of context (13/24 tokens)
============================================================
```

### 대시보드 주요 화면

| 탭 | 기능 |
|---|---|
| **Overview** | 컴포넌트별 토큰 분포를 바 차트 + treemap으로 시각화 |
| **Messages** | 각 메시지의 role, 토큰 수, 내용 미리보기 테이블 |
| **Diff** | 두 API 호출 간 컨텍스트 변화 비교 (추가/삭제/변화량) |

`Load Demo` 버튼 하나로 3개 샘플 데이터 주입 → 즉시 체험 가능

<!--
실행하면 콘솔에 호출마다 토큰 breakdown이 찍힌다. system이 54%를 쓰고 있으면 경고가 뜬다. 대시보드는 3개 탭인데, Overview에서 전체 분포를 보고, Messages에서 메시지 하나하나를 확인하고, Diff에서 대화가 진행되면서 컨텍스트가 어떻게 바뀌었는지 비교할 수 있다. Load Demo 버튼이 있어서 API 키 없이도 바로 체험해볼 수 있다.
-->

## Key Decisions & Lessons

### 기술 판단

| 판단 | 선택 | 이유 |
|------|------|------|
| 프론트엔드 | vanilla JS (D3.js 미사용) | CSS flex 기반 트리맵으로 충분, 의존성 최소화 |
| 데이터 저장 | 인메모리 | 프로토타입에 DB는 과잉 — 프로세스 종료 시 초기화로 충분 |
| XSS 대응 | innerHTML → DOM API 전면 교체 | 보안 훅에서 경고 → textContent 기반으로 리팩토링 |

### 심의 점수 (Spec 단계)

| 항목 | 점수 |
|------|:----:|
| 문제 진정성 (Authenticity) | 4.3 / 5 |
| 프로토타입 적합성 (Prototypability) | 4.3 / 5 |
| 신선도 (Freshness) | 4.0 / 5 |
| 학습 가치 (Learning Value) | 3.7 / 5 |

패널 결과: **만장일치 승인**

<!--
기술 판단 중에 인상적이었던 건 D3.js를 안 쓴 거다. 처음에는 트리맵이면 D3가 필요하지 않나 싶었는데, CSS flex로 충분했다. 의존성을 하나 줄이면 유지보수가 확 줄어든다. 그리고 innerHTML을 쓰다가 보안 훅에서 XSS 경고가 떴는데, 이걸 DOM API로 전면 교체했다. 프로토타입이라도 보안은 챙겨야 한다는 교훈. 심의 점수는 문제 진정성이 4.3으로 꽤 높았다. 패널이 만장일치로 승인했다.
-->

## Results & Future

### 성과 (5/5 완료 기준 통과)

- ✅ 로컬 프록시 인터셉트 + 전달 (mock/real 모드)
- ✅ role별 분류 + tools 정의 tiktoken 카운팅 (5개 컴포넌트)
- ✅ 웹 대시보드 트리맵/바차트 시각화
- ✅ 연속 호출 간 컨텍스트 diff
- ✅ 50% 초과 시 경고 표시

### 한계점
- OpenAI API 포맷만 지원 (Anthropic API 미지원)
- 스트리밍 응답은 분석하지 않음 (요청만 분석)
- 인메모리 저장 — 프로세스 종료 시 데이터 소실

### 프로덕트가 되려면
- **멀티 프로바이더 지원**: Anthropic, Gemini 등 API 포맷 확장
- **영속 저장 + 타임라인**: SQLite로 히스토리 누적, 시간축 분석
- **IDE 통합**: VS Code extension으로 에디터 안에서 컨텍스트 모니터링
- **자동 최적화 제안**: "system prompt를 20% 줄이면 대화 3턴 더 유지 가능" 같은 인사이트
