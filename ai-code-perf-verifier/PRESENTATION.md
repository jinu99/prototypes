**스택**: Python, AST, Git, Rich, uv
**날짜**: 2026-03-08

## Background

### AI 코드 생성 시대의 사각지대

- AI 코딩 도구(Copilot, Cursor 등)가 일상이 된 시대
- 생성된 코드는 **컴파일되고, 테스트를 통과**한다
- 하지만 **비기능적 품질**(성능, 메모리)은 아무도 안 본다

### 왜 지금 이슈인가

- SQLite를 LLM으로 재작성했더니 기본 키 조회가 **20,000배 느린** 사례
- AI 생성 코드의 **검증 부채(verification debt)**가 누적되는 중
- "돌아가니까 OK" → 프로덕션에서 성능 장애로 돌아온다

<!--

## Solution

### 접근법

**"Git diff에서 변경 함수를 자동으로 찾고, 기존 테스트로 성능을 측정한다"**

### 기존 도구와의 차이

| 기존 도구 | 한계 | 우리 접근 |
|-----------|------|-----------|
| pytest-benchmark | 변경분 자동 식별 없음 | Git diff → AST로 변경 함수만 타겟 |
| Greptile | AI 리뷰 품질 벤치마크 | 실제 실행 시간/메모리 비교 |
| Exceeds AI | SaaS, 실시간 아님 | 로컬 CLI, 즉시 실행 |

### 핵심 아이디어

벤치마크를 새로 만들지 않는다. **이미 있는 테스트를 벤치마크로 재활용**한다.

<!--
기존에도 벤치마크 도구는 있다. pytest-benchmark, hyperfine 같은 것들. 근데 이것들은 "어떤 함수를 측정할지"를 개발자가 직접 지정해야 한다. 우리 접근은 다르다. Git diff를 파싱해서 변경된 함수를 AST 레벨에서 자동으로 찾고, 그 함수를 커버하는 기존 테스트를 찾아서 벤치마크로 돌린다. 별도 벤치마크를 작성할 필요가 없다는 게 핵심이다.
-->

## Architecture

```
┌─────────────────────────────────────────────────────────────────┐
│                        perf-verify CLI                         │
└──────────┬──────────────────────────────────────────────────────┘
           │
           ▼
┌─────────────────────┐    git diff --unified=0    ┌────────────┐
│   Diff Parser       │◀──────────────────────────▶│    Git     │
│  (diff_parser.py)   │                            │ Repository │
└──────────┬──────────┘
           │ Changed .py files + line numbers
           ▼
┌─────────────────────┐
│   AST Analyzer      │    Maps changed lines to
│  (ast_analyzer.py)  │    functions/methods via Python AST
└──────────┬──────────┘
           │ List of changed functions
           ▼
┌─────────────────────┐    git show ref:file    ┌────────────────┐
│   Benchmarker       │◀───────────────────────▶│ Before Source  │
│  (benchmarker.py)   │    time.perf_counter    └────────────────┘
│                     │    tracemalloc
└──────────┬──────────┘
           │ before/after benchmark results
           ▼
┌─────────────────────┐
│   Reporter          │    Rich table output
│  (reporter.py)      │    exit code: 0=OK, 1=regression
└─────────────────────┘
```

<!--
구조는 꽤 단순하다. 네 개의 모듈이 파이프라인으로 연결된다. Diff Parser가 git diff를 파싱해서 변경된 파일과 라인을 뽑고, AST Analyzer가 그 라인이 어떤 함수에 속하는지 찾는다. Benchmarker가 git show로 변경 전 소스를 가져와서 before/after를 각각 측정하고, Reporter가 비교 테이블을 찍어준다. 외부 의존성은 Rich 하나뿐이고, 나머지는 전부 Python 표준 라이브러리다.
-->

## Demo

### 시나리오: fibonacci O(n) → O(2^n), sort 내장 → 버블 정렬

```
        Changed Functions
┌──────────────┬────────────────┬───────┐
│ Function     │ File           │ Lines │
├──────────────┼────────────────┼───────┤
│ fibonacci    │ algorithms.py  │ 4-12  │
│ sort_data    │ algorithms.py  │ 15-23 │
└──────────────┴────────────────┴───────┘

          Performance Comparison
┌──────────────┬────────┬────────┬───────┬────────┬──────────────┐
│ Function     │ Before │ After  │ Ratio │ Mem Δ  │ Status       │
│              │ (ms)   │ (ms)   │       │ (KB)   │              │
├──────────────┼────────┼────────┼───────┼────────┼──────────────┤
│ fibonacci    │  0.03  │ 18.42  │ 614x  │ +2.1   │ ⚠ SLOWER     │
│ sort_data    │  0.15  │  8.71  │ 58.1x │ +0.3   │ ⚠ SLOWER     │
└──────────────┴────────┴────────┴───────┴────────┴──────────────┘

⚠ Performance regression detected! (threshold: 2.0x)
Exit code: 1
```

<!--
데모에서는 일부러 나쁜 변경을 넣어봤다. fibonacci를 DP에서 순수 재귀로, sort를 내장 정렬에서 버블 정렬로 바꿨다. 결과를 보면 fibonacci가 614배, sort_data가 58배 느려진 걸 정확히 잡아낸다. threshold 기본값이 2배인데, 이걸 넘으면 exit code 1을 반환해서 CI에서 자동으로 블록할 수 있다.

## Key Decisions & Lessons

### 기술 판단

| 판단 | 선택 | 이유 |
|------|------|------|
| 벤치마크 방식 | 기존 테스트 재활용 | 자동 입력 생성은 범위 밖. 테스트가 이미 유의미한 입력을 제공 |
| 의존성 | Rich만 사용 | ast, subprocess, tracemalloc 모두 표준 라이브러리로 해결 |
| 변경 함수 식별 | AST 파싱 | regex 매칭보다 정확. 클래스 메서드까지 처리 가능 |

### 시행착오

- flat layout에서 모듈 import 실패 → 패키지 구조로 전환
- 터미널 테이블이 폭 초과 → 컬럼 8개에서 6개로 축소

### 심의 점수

문제 진정성 **4.0**/5 · 프로토타입 적합성 **3.3**/5 · 학습 가치 **3.7**/5
패널 만장일치 승인

<!--
몇 가지 판단이 있었다. 가장 큰 건 벤치마크를 어떻게 돌릴 것인가였다. 자동으로 입력을 생성하는 건 그 자체가 하나의 프로젝트 규모라서 범위에서 뺐다. 대신 기존 테스트를 벤치마크로 재활용하는 방식을 택했다. 테스트가 이미 유의미한 입력을 갖고 있으니까. 솔직히 테스트가 없는 함수는 측정할 수 없다는 한계가 있는데, 그건 받아들일 수 있는 트레이드오프라고 봤다.
-->

## Results & Future

### 성과 (5/5 통과)

- [x] CLI로 변경 함수 목록 출력 (변경 안 된 함수는 정확히 제외)
- [x] 변경 전/후 테스트 기반 벤치마크 실행
- [x] before/after 비교 테이블 출력
- [x] 임계값 초과 시 경고 + exit code 1
- [x] 샘플 프로젝트 e2e 데모 동작

### 한계점

- Python 전용 (다른 언어 미지원)
- 테스트가 없는 함수는 측정 불가
- 벤치마크 입력 자동 생성 미지원

### 프로덕트가 되려면

- **다언어 지원**: Tree-sitter로 AST 파싱 일반화
- **CI 통합**: GitHub Action으로 PR마다 자동 실행
- **벤치마크 자동 생성**: LLM으로 테스트 입력 생성 → 테스트 없는 함수도 커버
- **이력 추적**: 커밋별 성능 추이 시각화

<!--
