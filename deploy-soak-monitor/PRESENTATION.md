# Deploy Soak Monitor

**배포 후 자동 soak 윈도우 모니터링 — pod 상태/로그 실시간 감시로 이상 징후를 잡아내는 CLI 도구**

- **카테고리**: DevOps / Kubernetes Observability
- **스택**: Python 3.12, asyncio, 외부 의존성 0개
- **날짜**: 2026-03-14

<!--

## Background

### 배포 후 15분, 개발자는 뭘 하고 있나

- 프로덕션 배포 직후 **10~15분**간 개발자가 수동으로 감시하는 "soak 구간"이 존재
- Grafana 대시보드, 에러 로그, 알림 채널을 **번갈아가며** 모니터링
- 야간 배포, 하루 여러 번 배포하는 팀일수록 부담이 기하급수적으로 증가
- Kubernetes 환경에서는 kubectl, k9s, Lens, 브라우저를 **전전하며** 도구 전환

> 배포는 자동화됐는데, 배포 직후 감시는 여전히 수동이다.

<!--

## Solution

### 모든 배포에 자동으로 붙는 가벼운 soak monitor

**핵심 아이디어**: 서비스 메시 없이, "배포 후 N분간 자동 감시 → 이상 시 알림"

| 기존 솔루션 | 한계 | 이 도구의 접근 |
|------------|------|---------------|
| K8sGPT | on-demand 진단 (사후) | 배포 이벤트 **자동 감지** 후 실시간 감시 |
| Argo Rollouts / Flagger | 서비스 메시 필요, setup 부담 | 의존성 0개, CLI 하나로 즉시 사용 |
| Botkube | 프리미엄, Slack 의존 | 터미널 기반, 롤백 명령까지 제안 |

> **검증 목표**: 배포 후 MTTD(평균 감지 시간)를 5분 이내로 줄일 수 있는가?

<!--
기존 도구들을 보면, K8sGPT는 이미 터진 문제를 진단해주는 거고, Argo Rollouts는 카나리 배포 자동화인데 Istio 같은 서비스 메시가 깔려 있어야 한다. 소규모 팀이 쓰기엔 setup 부담이 크다. 이 도구가 노리는 건 그 사이의 빈 공간이다. 그냥 배포하면 알아서 감시 시작하고, 이상하면 알려주고, 롤백 명령까지 제안해주는 거. 서비스 메시도 필요 없고, 의존성도 없다. 검증하고 싶었던 건, 이 자동 감시만으로 장애 감지 시간을 5분 이내로 줄일 수 있는가 하는 거다.
-->

## Architecture

```
┌─────────────────────────────────────────────────────────────────┐
│                          CLI (cli.py)                           │
│                   argparse: watch / scenarios                   │
└──────────────────────────┬──────────────────────────────────────┘
                           │ 명령 파싱
                           ▼
┌──────────────────────────────────────────────────────────────────┐
│                    Demo Runner (demo.py)                         │
│        시나리오 선택: healthy │ oom │ crashloop │ error_logs      │
└──────────────┬──────────────────────────────────┬────────────────┘
               │ create_deployment()              │ rolling_update()
               ▼                                  ▼
┌──────────────────────────────────────────────────────────────────┐
│                 Simulated Cluster (cluster.py)                   │
│   Deployment/Pod 생성 → 장애 주입 (OOM/CrashLoop/Log) → Event 발행  │
└──────────────────────────────────────────┬───────────────────────┘
                                           │ watcher callback
                                           ▼
┌──────────────────────────────────────────────────────────────────┐
│                   Soak Monitor (monitor.py)                      │
│   Event 수신 → Pod 상태 확인 → 로그 분석 (PatternMatcher, 9개 정규식)  │
└──────────────────────────────────────────┬───────────────────────┘
                                           │ anomaly / pattern_alert
                                           ▼
┌──────────────────────────────────────────────────────────────────┐
│                     Reporter (reporter.py)                       │
│   ✓ Pod 시작 │ ↻ Rolling Update │ ✖ 이상 징후 │ ⚠ Anomaly         │
│   Progress Bar [████░░░░] 40%  │  ALL CLEAR / SOAK FAILED       │
└──────────────────────────────────────────────────────────────────┘
```

<!--
구조는 5개 모듈로 나뉜다. 위에서부터 CLI가 명령을 받고, Demo Runner가 시나리오를 선택하고, Simulated Cluster가 K8s를 흉내 낸다. 여기서 핵심은 cluster.py가 이벤트를 발행하면 monitor.py가 콜백으로 받아서 분석하는 구조라는 거다. 나중에 시뮬레이터를 실제 kubernetes client로 바꾸면 그대로 프로덕션 도구가 된다. PatternMatcher가 9개 정규식으로 로그를 분석하고, 최종 결과는 Reporter가 ANSI 컬러로 터미널에 출력한다.
-->

## Demo

### OOMKilled 감지 시나리오

```
  ✓ New pod web-api-2-2959 started (revision 2)
  ✖ Pod web-api-2-2959 OOMKilled (memory limit exceeded)

  ────────────────────────────────────────────────────────
  ⚠  ANOMALY DETECTED
     Pod: web-api-2-2959
     Type: OOMKilled
     Detail: Container killed by OOM killer

     💡 Suggested rollback:
     $ kubectl rollout undo deployment/web-api -n default
  ────────────────────────────────────────────────────────

════════════════════════════════════════════════════════════
  ❌ SOAK FAILED — Issues detected
  Anomalies: 1
    1. OOMKilled: Container killed by OOM killer
════════════════════════════════════════════════════════════
```

**4가지 시나리오**: `healthy` (ALL CLEAR) · `oom` · `crashloop` · `error_logs`

<!--
데모를 보면, OOM 시나리오에서 pod가 뜨고 3초 후에 OOMKilled가 발생한다. 모니터가 즉시 감지해서 어떤 pod에서 무슨 문제가 생겼는지 보여주고, 롤백 명령까지 제안한다. 실제로 돌려보면 터미널에 컬러로 나오는데, 꽤 직관적이다. 총 4가지 시나리오를 지원하는데, 정상 배포부터 OOM, CrashLoop, 에러 로그 패턴까지 전부 시뮬레이션으로 동작한다. K8s 클러스터가 없어도 된다.

## Key Decisions & Lessons

### 기술 판단

| 판단 | 이유 |
|------|------|
| **Go 대신 Python** 선택 | Go/kubectl/kind 모두 미설치 환경. Python 3.12 + uv로 즉시 시작 |
| **K8s 시뮬레이터** 방식 | 실제 클러스터 없이 전체 흐름 검증. 인터페이스 분리로 추후 교체 용이 |
| **외부 의존성 0개** | 표준 라이브러리(asyncio, re, argparse)만으로 전체 구현 |

### 시행착오

- error_logs 시나리오에서 `connection_refused` + `error_generic` **중복 매칭** 발생
- → 가장 높은 severity 패턴만 보고하도록 수정 (priority map 기반 필터링)

### 심의 점수

| 항목 | 점수 |
|------|------|
| 문제 진정성 (Authenticity) | 4.0 / 5 |
| 프로토타입 적합성 (Prototypability) | 4.0 / 5 |
| 신선도 (Freshness) | 3.0 / 5 |
| 학습 가치 (Learning Value) | 4.0 / 5 |

<!--
스택 선택에서 원래 spec은 Go를 권장했는데, 환경에 Go가 없어서 Python으로 갔다. 솔직히 이 판단이 오히려 좋았던 게, asyncio로 이벤트 시스템 만드는 게 꽤 깔끔하게 떨어졌다. 시뮬레이터 방식도 마찬가지다. 실제 kind 클러스터를 띄우는 대신 시뮬레이터로 이벤트를 발행하는 구조를 만들었는데, 덕분에 핵심 로직인 감지에서 알림까지의 흐름을 클러스터 없이 검증할 수 있었다. 한 가지 시행착오가 있었는데, 에러 로그 분석에서 한 줄이 여러 패턴에 매칭되는 문제가 있었다. severity 기반 필터링으로 해결했다.
-->

## Results & Future

### 성과

- [x] `soak watch <namespace>` — Deployment 변경 자동 감지
- [x] 새 pod 로그 스트리밍 + 에러 패턴 매칭 (9개 정규식)
- [x] soak 윈도우 + `--duration` 플래그 지원
- [x] 이상 감지 시 경고 + `kubectl rollout undo` 제안
- [x] 4개 장애 시나리오 데모 동작 (healthy, oom, crashloop, error_logs)
- **심의 패널**: 만장일치 승인 · 완료 기준 전항 통과

### 한계

- 실제 K8s 클러스터 연동 미구현 (시뮬레이터만)
- Slack/webhook 알림 미연동 (터미널 출력만)
- 환경 간 설정 드리프트 탐지 미포함 (scope 축소)
- 자동 롤백은 명령 제안만 (실행은 사람이)

### 프로덕트가 되려면

1. `cluster.py` → 실제 `kubernetes` client 교체 (인터페이스 동일)
2. Slack/PagerDuty webhook 알림 연동
3. Prometheus 메트릭 기반 이상 탐지 추가
4. CI/CD 파이프라인 연동 (배포 이벤트 자동 트리거)
