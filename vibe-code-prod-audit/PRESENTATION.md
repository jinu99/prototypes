# vibe-audit

**tree-sitter 기반 바이브코딩 프로젝트 프로덕션 준비도 감사 CLI**

- 카테고리: Developer Tooling / Code Quality
- 스택: Python, tree-sitter, uv, argparse
- 날짜: 2026-03-02

<!--

## Background

- AI 코딩 도구(Cursor, Copilot, Claude Code)로 **"동작하는 프로토타입"**을 만드는 건 쉬워졌다
- 그런데 동작하는 것과 **프로덕션에 나갈 수 있는 것**은 다른 문제
- 헬스체크, 에러 핸들링, 테스트, 환경변수 관리, CORS — 이런 건 AI가 알아서 넣어주지 않는다
- 솔로 개발자나 바이브코더는 이 격차를 인지하지 못하거나, 인지해도 메우는 데 수주가 걸린다

<!--
바이브코딩이라는 말이 나올 정도로 AI로 코드 짜는 게 보편화됐다. 근데 이렇게 만든 코드가 프로덕션에 바로 나갈 수 있냐는 별개의 문제다. 사람으로 치면 요리를 할 줄 아는 것과 식당을 운영할 수 있는 것의 차이랄까. 요리만 하면 위생 검사, 소방 점검, 식자재 관리 같은 건 빠진다. 바이브코딩도 마찬가지다. 동작은 하는데 헬스체크도 없고, 테스트도 없고, 에러 핸들링도 없다.
-->

## Pain Point

커뮤니티에서 반복적으로 나오는 고통들:

| 출처 | Signal | Pain Point |
|------|:------:|------------|
| Hacker News | ★★★ | 바이브코딩 프로토타입에서 프로덕션 수준의 스펙을 역추출할 도구가 없다 |
| r/SideProject | ★★★ | 빠르게 배포된 앱이 업타임 모니터링·인시던트 관리를 전부 생략한다 |
| r/SideProject | ★★★ | 솔로 개발자가 QA 경험 없이 E2E 테스트를 시작하기엔 진입장벽이 너무 높다 |
| r/SideProject | ★★★ | PR 없이 IDE 내에서 코드 리뷰를 받을 저렴한 방법이 없다 |

## Solution

**한 줄 요약**: 프로젝트 디렉토리를 스캔해서 프로덕션 준비도를 점수화하고, 부족한 부분의 코드를 생성한다.

### 기존 솔루션과의 차이

| 기존 | vibe-audit |
|------|-----------|
| VibeCheck ($79, Mac 전용) — 체크리스트만 보여줌 | 코드 분석 + **보완 코드 자동 생성** |
| VIBECODE AUDIT — 사람이 리뷰 (24-48시간) | tree-sitter 기반 **즉시 자동 진단** |
| CodeRabbit 등 — PR 기반, 솔로 개발자에 부적합 | **로컬 CLI**, PR 없이 동작 |

### 핵심 아이디어
- LLM이 아닌 **tree-sitter AST 파싱** → 결정론적, 빠름, API 키 불필요
- 진단에서 끝나지 않고 **보완 코드까지 생성**

<!--
접근법은 꽤 단순하다. tree-sitter로 코드의 AST를 파싱해서 라우트, 미들웨어, 에러 핸들러 같은 걸 추출하고, 체크리스트로 점수를 매긴다. 기존에 비슷한 도구가 있긴 한데, 대부분 체크리스트를 보여주거나 사람이 직접 리뷰하는 형태다. 이 도구는 진단하고 끝나는 게 아니라 부족한 부분의 코드를 바로 생성해준다. 그리고 LLM을 안 쓰니까 API 키도 필요 없고, 결과가 결정론적이다. 같은 코드를 넣으면 항상 같은 점수가 나온다.
-->

## Architecture

```
┌─────────────────┐
│   CLI (cli.py)  │  argparse: scan <project-dir> [--json] [--output-dir]
└────────┬────────┘
         │
         ▼
┌─────────────────────────────────────────────────────┐
│              Scanner (scanner.py)                    │
│                                                     │
│  project-dir ──▶ find_python_files()                │
│                       │                             │
│                       ▼                             │
│              tree-sitter Parser                     │
│                       │                             │
│          ┌────────────┼────────────┐                │
│          ▼            ▼            ▼                │
│    Route 추출    Middleware    Error Handler         │
│   (@app.get,     검출         검출                  │
│    @router.post)                                    │
└───────────────────────┬─────────────────────────────┘
                        │
                        ▼
┌─────────────────────────────────────────────────────┐
│           Checklist (checklist.py)                   │
│  9개 항목 평가 (가중치 기반 점수화: 0-100)          │
│  Structure(20) │ Reliability(35) │ Quality(20)      │
│  Security(20)  │ Deployment(5)                      │
└───────────────────────┬─────────────────────────────┘
                        │
              ┌─────────┴─────────┐
              ▼                   ▼
┌──────────────────┐  ┌────────────────────────┐
│  Terminal Report  │  │  Generator (generator.py)│
│  (컬러 바, 점수)  │  │  실패 항목별 보완 코드:  │
│  또는 --json     │  │  health.py, test_api.py, │
│                  │  │  Dockerfile, config.py   │
└──────────────────┘  └────────────────────────┘
```

<!--
구조는 세 단계다. 먼저 scanner가 tree-sitter로 Python 파일을 파싱해서 라우트, 미들웨어, 에러 핸들러를 추출한다. 그 결과를 checklist가 받아서 9개 항목으로 점수를 매긴다. 가중치가 다른데, 헬스체크나 에러 핸들링 같은 reliability 항목이 35점으로 가장 높다. 마지막으로 generator가 실패한 항목에 대해 바로 쓸 수 있는 보완 코드를 생성한다. 전체가 로컬에서 돌아가고 외부 의존성은 tree-sitter 하나뿐이다.
-->

## Key Decisions & Lessons

### 기술 판단

| 판단 | 이유 |
|------|------|
| **tree-sitter** (LLM 대신) | 결정론적 분석, API 키 불필요, 빠름. AST 레벨에서 패턴 매칭이면 충분 |
| **FastAPI 단일 타겟** | 바이브코딩에서 가장 많이 쓰이는 Python 웹 프레임워크. 범위 축소가 품질을 높임 |
| **f-string 코드 생성** (Jinja2 대신) | 생성할 템플릿이 5종뿐. 외부 의존성 추가 대비 이득 없음 |

### 시행착오
- `hatchling.backends` 오타로 빌드 실패 → `hatchling.build`로 수정
- JSON 모드에서 status 메시지가 stdout에 섞임 → stderr로 분리
- 재스캔 시 `generated/` 디렉토리를 포함하는 문제 → skip_dirs에 추가

### 심의 점수
문제 진정성 **4.0**/5 · 학습 가치 **4.3**/5 · 프로토타입 적합성 **3.3**/5

<!--
기술적으로 가장 중요한 판단은 LLM 대신 tree-sitter를 쓴 거다. 코드 분석에 LLM을 쓰면 결과가 매번 달라지고, API 키도 필요하고, 느리다. 근데 우리가 하려는 건 라우트 추출이나 미들웨어 감지 같은 패턴 매칭이라 AST 파싱이면 충분하다. 시행착오도 있었는데, 대부분 소소한 것들이다. 재스캔할 때 생성된 보완 코드 디렉토리를 다시 스캔하는 문제가 있었는데, skip_dirs에 추가해서 해결했다. 심의에서 학습 가치가 4.3으로 꽤 높게 나왔다. tree-sitter를 실전에서 써볼 수 있는 좋은 케이스였다.
-->

## Results & Future

### 성과
- ✅ tree-sitter로 라우트 추출 + 프로덕션 준비도 점수(0-100) 출력
- ✅ 9개 체크리스트 항목별 통과/미통과 표시
- ✅ 미통과 항목에 대해 5종 보완 코드 자동 생성
- ✅ 샘플 프로젝트 2개에서 E2E 데모 정상 동작
- **4/4 완료 기준 통과 → SUCCESS**

### 한계점
- FastAPI 단일 프레임워크만 지원 (Express, Next.js 등 미지원)
- 생성된 테스트의 실행 가능 여부는 보장하지 않음 (구조만 생성)
- 스펙 역추출, IDE 연동은 v2 범위

### 프로덕트가 되려면
- 멀티 프레임워크 지원 (Express, Django, Next.js)
- CI/CD 파이프라인 연동 (GitHub Actions에서 자동 실행)
- 생성된 테스트가 실제로 통과하는지까지 검증
- VS Code 확장으로 에디터 내 실시간 점수 표시
