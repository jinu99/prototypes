# Agent Token Waste Analyzer

**AI 코딩 에이전트의 토큰 낭비 패턴을 진단하고 최적화 포인트를 제시하는 CLI 도구**

- Category: Developer Tools / AI Agent Observability
- Stack: Python, Rich, uv
- Date: 2026-03-12

## Background

- AI 코딩 에이전트(Claude Code, Cursor 등)가 개발 워크플로우의 중심이 되고 있다
- 에이전트는 작업 전에 코드베이스를 탐색해야 한다 — 파일 읽기, 검색, 컨텍스트 수집
- 문제는 이 탐색 과정이 **체계적으로 비효율적**이라는 것
- 토큰 예산의 절반이 실제 작업이 아닌 컨텍스트 수집에 소모되는 경우가 흔하다
- 기존 도구(Langfuse, Portkey)는 "얼마나 썼는가"를 보여주지만, **"어디서 왜 낭비인가"는 알려주지 않는다**

<!--
AI 코딩 에이전트를 쓰다 보면, 실제로 코드를 작성하는 시간보다 코드베이스를 탐색하는 시간이 더 긴 경우가 꽤 있다.
사람으로 치면, 일을 시작하기 전에 책상 정리만 한 시간 하는 거다.
기존 모니터링 도구들은 총 비용을 보여주는데, 결국 "비싸네"만 알 뿐 원인을 모른다.
프로파일러가 필요한 시점이다.
-->

## Solution

**"얼마나 썼는가" → "어디서 왜 낭비인가"**

핵심 전환: 모니터링(사후 추적)에서 **프로파일링(원인 진단)**으로

세 가지 낭비 패턴을 자동 감지한다:

| 패턴 | 설명 |
|------|------|
| `repeated_read` | 같은 파일을 세션 내에서 여러 번 Read |
| `unused_search` | Grep/Glob 결과를 이후 행동에서 활용하지 않음 |
| `duplicate_context` | 매 턴마다 대량의 캐시를 재로딩, 극소량의 출력만 생성 |

그리고 세션별 **유효 토큰 비율**(effective token ratio)을 산출한다.

<!--
기존 도구와 다른 점은 하나다. Langfuse 같은 도구는 "이번 달에 토큰을 20만 개 썼다"를 알려준다. 우리 도구는 "그 20만 개 중 47%가 같은 파일을 반복해서 읽는 데 쓰였다"를 알려준다.
결국 이건 프로파일러다. CPU 프로파일러가 "어떤 함수에서 시간을 잡아먹는가"를 보여주듯, 토큰 프로파일러가 "어떤 패턴에서 토큰을 잡아먹는가"를 보여주는 거다.
-->

## Architecture

```
┌──────────────────────────────────────────────────────────────────┐
│                     CLI (run.py / main.py)                       │
│               list · analyze <path> · latest                     │
└───────────────────────────┬──────────────────────────────────────┘
                            │
                            ▼
┌──────────────────────────────────────────────────────────────────┐
│                     Parser (parser.py)                            │
│   ~/.claude/projects/**/*.jsonl  ──▶  SessionData                │
│     ├─ messages[], tool_calls[], token usage 집계                 │
└───────────────────────────┬──────────────────────────────────────┘
                            │
                            ▼
┌──────────────────────────────────────────────────────────────────┐
│                    Analyzer (analyzer.py)                         │
│   ┌────────────────┐ ┌───────────────┐ ┌──────────────────┐      │
│   │ repeated_read  │ │ unused_search │ │ duplicate_context│      │
│   └────────┬───────┘ └───────┬───────┘ └────────┬─────────┘      │
│            └─────────────────┼──────────────────┘                │
│                    WastePattern[] + OptimizationSuggestion[]      │
└───────────────────────────┬──────────────────────────────────────┘
                            │
                            ▼
┌──────────────────────────────────────────────────────────────────┐
│                   Dashboard (dashboard.py)                        │
│            Rich 터미널 UI — 요약, 핫스팟, 제안, 등급              │
└──────────────────────────────────────────────────────────────────┘
```

- **Parser**: JSONL을 라인별로 파싱, `tool_use` 타입에서 tool call 시퀀스 추출, `usage` 필드에서 토큰 집계
- **Analyzer**: 3개의 독립적인 패턴 감지기가 각각 휴리스틱 기반으로 낭비를 식별
- **Dashboard**: Rich Panel/Table로 한눈에 보이는 터미널 대시보드 구성

의도적으로 단순하게 가져갔다. 외부 의존성은 Rich 하나뿐이다.

## Key Decisions & Lessons

**1. 휴리스틱 기반 감지 vs LLM 기반 감지**
- LLM에 로그를 넘기면 정확하겠지만, 그 자체가 토큰 낭비다
- 규칙 기반 휴리스틱으로 충분히 유의미한 패턴을 잡을 수 있었다

**2. 캐시 토큰의 낭비 판단 기준**
- `cache_read > 95%` + `output < 1%`이면 "컨텍스트만 재로딩하고 일은 안 한 턴"으로 판단
- 보수적으로 절반만 낭비로 산정 — 완벽한 정답은 없다

**3. 스택: Python + Rich, uv 관리**
- JSONL 파싱은 표준 라이브러리 `json`으로 충분, Rich가 터미널 대시보드에 최적
- 외부 의존성 최소화가 프로토타입에서는 올바른 판단

**심의 점수**: 문제 진정성 4.7 · 프로토타입 적합성 4.0 · 신선도 3.0 · 학습 가치 3.7

<!--

## Results & Future

### 성과 (5/5 완료 기준 통과)
- ✅ JSONL 세션 로그 파싱 → tool call 시퀀스 추출
- ✅ 반복 파일 읽기 패턴 감지 + 중복 횟수/낭비량 리포트
- ✅ 세션별 유효 토큰 비율 산출
- ✅ 터미널 대시보드: 핫스팟 Top 5 + 최적화 제안
- ✅ 실제 세션 로그 e2e 데모 동작 (Grade D, 47.3% waste)

### 한계
- Claude Code 로그만 지원 (Cursor, Windsurf 등 미지원)
- 사후 분석만 가능 (실시간 모니터링 없음)
- 패턴 감지가 휴리스틱이라 false positive 가능

### 프로덕트가 되려면
- 멀티 에이전트 로그 포맷 통합 파서
- 시계열 분석: 세션 간 낭비율 추이 트래킹
- CI 통합: 세션 효율이 임계치 이하면 경고
- 실시간 모드: 세션 진행 중 낭비 감지 + 중단 제안
